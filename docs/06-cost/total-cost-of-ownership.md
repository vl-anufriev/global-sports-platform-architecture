# 16. Стоимость владения системой

## 1. Цель оценки

Необходимо оценить стоимость владения системой в первый, второй и пятый годы
с учётом роста пользовательской базы и объёма данных.

Исходное задание не содержит точного прогноза:

- количества пользователей;
- количества тренировок;
- размера тренировочных данных;
- сетевого трафика;
- необходимого уровня availability.

Поэтому используется сценарная модель.

Приведённые значения являются архитектурной оценкой порядка стоимости,
а не коммерческим предложением конкретного cloud-провайдера.

Стоимость команды разработки в расчёт не включается.

Рассматриваются преимущественно вычислительные ресурсы и эксплуатационная
инфраструктура.

---

# 2. Предположения

Для расчёта принимается следующий сценарий роста.

| Показатель | Год 1 | Год 2 | Год 5 |
|---|---:|---:|---:|
| Monthly Active Users | 100 000 | 500 000 | 5 000 000 |
| Daily Active Users | 25 000 | 125 000 | 1 250 000 |
| Тренировок на активного пользователя в месяц | 8 | 8 | 8 |
| Тренировок в месяц | 800 000 | 4 000 000 | 40 000 000 |
| Средний объём данных тренировки | ~0.4 MB | ~0.4 MB | ~0.4 MB |

Средний размер тренировки включает приблизительную оценку:

- основной записи тренировки;
- временных показателей;
- GPS-данных;
- метрик устройств.

Реальный размер зависит от частоты измерений и политики хранения данных.

---

# 3. Рост тренировочных данных

## Год 1

```text
800 000 workouts/month
× 12
× 0.4 MB
≈ 3.8 TB/year
```

## Год 2

```text
4 000 000 workouts/month
× 12
× 0.4 MB
≈ 19.2 TB/year
```

## Год 5

```text
40 000 000 workouts/month
× 12
× 0.4 MB
≈ 192 TB/year
```

Это только новые сырые тренировочные данные.

Дополнительно система хранит:

- профили;
- социальные связи;
- агрегаты;
- рейтинги;
- achievements;
- observability;
- backups.

Поэтому фактический объём хранения будет выше.

## Data Lifecycle Assumption

Если хранить всю raw telemetry бессрочно, объём и стоимость будут постоянно
накапливаться. Показатели 3.8 / 19.2 / 192 TB описывают новые данные за соответствующий
год, а не полный объём хранения на конец года.

Концептуальная политика хранения:

| Уровень | Данные | Подход |
|---|---|---|
| Hot | недавние тренировки, активные соревнования, часто используемые данные | быстрое operational storage для пользовательских сценариев |
| Warm / Archive | старые raw metrics, редко используемые GPS / telemetry, исторические данные | более дешёвые уровни хранения с допустимой задержкой доступа |
| Aggregated | долгосрочная статистика и спортивные тенденции | хранение агрегатов там, где не требуется полная raw telemetry |

Удаление или архивирование должно учитывать бизнес-ценность, privacy и
legal / compliance requirements. Сроки хранения не заданы: их необходимо
определить перед production-запуском, без предположений о юридических сроках.

Накопленный объём включает сохраняемые данные предыдущих лет и новые данные
текущего года, за вычетом удалённых данных. Перевод в архив меняет стоимость
и доступность, но сам по себе не уменьшает общий логический объём.
Дополнительное место занимают индексы, реплики, backups и observability.
Прогноз для годов 3 и 4 отсутствует, поэтому точный накопленный объём к году 5
не рассчитывается.

Storage cost для Year 1 / Year 2 / Year 5 зависит не только от новых данных,
но и от retention policy, распределения по storage tiers и резервирования.
Приведённые ниже суммы предполагают управление lifecycle и требуют пересчёта
после утверждения сроков хранения.

# 4. Основные статьи затрат

Стоимость системы разделяется на несколько групп.

## Compute

- API Gateway;
- application services;
- async workers;
- background jobs.

## Databases

- основные доменные данные;
- read replicas;
- резервирование;
- backups.

## Event Infrastructure

- message broker;
- обработчики;
- очереди.

## Cache

Используется для:

- популярных данных;
- рейтингов;
- справочников;
- части read-моделей.

## Storage

- тренировочные данные;
- маршруты;
- пользовательский контент;
- backups;
- архивы.

## Network / CDN

- пользовательский трафик;
- изображения;
- публичный контент;
- региональная доставка данных.

## Observability

- logs;
- metrics;
- tracing;
- alerts.

## Security / Edge

- WAF;
- load balancing;
- secrets;
- security monitoring.

## Reference Resource Model

Это сценарная архитектурная модель, а не sizing для конкретного cloud provider.
Она связывает финансовые категории с ресурсами и их относительным развитием.
Типы VM, число экземпляров и тарифы не фиксируются: для точного расчёта нужны
нагрузочный профиль, SLO, retention policy и выбранный провайдер.

| Ресурсы | Финансовая категория | Year 1 | Year 2 | Year 5 |
|---|---|---|---|---|
| Application compute | Compute / API / Workers | небольшой горизонтально масштабируемый application pool в single primary region | больший пул приложений, выделение нагруженных доменов при необходимости | выделенное масштабирование Training и других критических доменов; потенциально multi-region |
| Async workers | Compute / API / Workers | небольшой пул фоновых consumers и Outbox Publisher | больше workers для Analytics, Gamification и Recommendations | независимые крупные пулы Analytics / Gamification, масштабирование по event throughput |
| Database compute / storage | Databases | managed relational / storage layer для доменных данных и outbox | увеличение мощности и read scaling | дополнительные мощности и read replicas; региональные данные только при выборе multi-region |
| Event broker | Event Broker + Cache | managed broker для базового потока событий | большая ёмкость и throughput broker | значительно больший event throughput и независимое масштабирование инфраструктуры событий |
| Distributed cache | Event Broker + Cache | базовый cache для востребованных read-сценариев | больше ёмкости для рейтингов и read-моделей | масштабирование cache по нагрузке, возможное региональное размещение |
| Object storage | Storage + Backups | несколько TB новых тренировочных данных в год (~3.8 TB); объекты и контент | ~19 TB новых данных в год; рост накопленного объёма | ~192 TB новых данных в год; lifecycle / archival storage становится обязательным условием сценарной оценки |
| Backup storage | Storage + Backups | резервные копии основного региона | рост объёма копий вслед за данными | существенный накопленный объём; стратегия DR зависит от RPO / RTO |
| Network egress | Network / CDN | пользовательский API и контент из основного региона | рост пользовательского трафика и внешних интеграций | большой исходящий трафик, возможный межрегиональный обмен |
| CDN | Network / CDN | Optional / Future, не обязательна для MVP; категория может включать только network | при подтверждённой потребности в глобальной доставке публичного контента | потенциально широкая доставка публичного контента через CDN |
| Observability storage / ingestion | Observability | централизованные logs, metrics, traces с ограниченным retention | увеличенный ingestion и объём диагностики | большой ingestion; sampling, агрегация и lifecycle ограничивают рост |
| Security / Edge | Security / Edge | защита периметра, load balancing, secrets | рост мощности edge и security monitoring | масштабирование защиты; потенциально несколько регионов |

Базовый сценарий начинается с одного региона. Multi-region и CDN остаются
возможностями развития (ADR-011 и ADR-012 — Proposed), даже если бюджет года 5
содержит резерв на такой рост. Год сам по себе не является основанием для их внедрения.

Суммы ниже — оценки порядка стоимости по финансовым категориям, а не результат
провайдерского калькулятора. Ресурсная модель объясняет состав и направления
роста затрат; фактическая ёмкость и цены должны быть проверены отдельно.
Размер outbox и стоимость publisher включены в Databases и Compute / API / Workers.
Основные доменные данные относятся к Databases, большие объекты и telemetry при
соответствующем размещении — к Storage + Backups; одни и те же данные не учитываются
дважды. Разделение хранения уточняется при физическом проектировании.

# 5. Год 1

## Архитектурный профиль

Система находится на раннем этапе.

Примерная пользовательская база:

`100 000 MAU`

Основная задача — не строить инфраструктуру на 5 миллионов пользователей заранее.

На данном этапе возможно:

- один основной cloud region;
- autoscaling;
- managed database;
- managed message broker;
- минимально необходимое резервирование.

## Оценка расходов

| Категория | В месяц | В год |
|---|---:|---:|
| Compute / API / Workers | $1 800 | $21 600 |
| Databases | $1 200 | $14 400 |
| Event Broker + Cache | $600 | $7 200 |
| Storage + Backups | $400 | $4 800 |
| Observability | $1 000 | $12 000 |
| Network / CDN | $800 | $9 600 |
| Security / Edge | $400 | $4 800 |
| **Итого** | **$6 200** | **$74 400** |

Для резервирования бюджета добавляется приблизительно 15%.

```text
$74 400 × 1.15 ≈ $85 600 / year
```

### Оценка года 1

**≈ $85 000 в год**

# 9. Почему стоимость не растёт строго линейно

Рост пользователей в 50 раз не обязан приводить к росту стоимости ровно
в 50 раз.

Причины:

- fixed costs существуют уже на первом этапе;
- крупные ресурсы обычно используются эффективнее;
- кеширование снижает нагрузку;
- CDN переносит часть трафика;
- старые данные можно переводить на более дешёвые storage tiers.

Одновременно на больших масштабах возникают новые затраты:

- multi-region;
- disaster recovery;
- observability;
- security;
- дополнительные replicas.

# 10. Оптимизация стоимости

## Autoscaling

Application services масштабируются в зависимости от реальной нагрузки.

---

## Data Lifecycle

Горячие данные:

- последние тренировки;
- активные соревнования.

Хранятся в быстром хранилище.

Старые данные могут переводиться в более дешёвый storage tier.

---

## Observability Sampling

Не требуется хранить полный distributed trace для каждого запроса.

Используется sampling.

---

## CDN

При подтверждённой необходимости статический и публичный контент доставляется
через CDN (ADR-012, Proposed).

---

## Асинхронная обработка

Фоновые задачи позволяют лучше использовать вычислительные ресурсы и
сглаживать пики нагрузки.

---

## Архивирование

Исторические данные, которые редко используются, могут храниться отдельно
от operational database.

---

# 11. Основные факторы неопределённости

Наибольшее влияние на реальную стоимость окажут:

1. реальное количество пользователей;
2. количество тренировок;
3. частота записи GPS и sensor metrics;
4. срок хранения сырых данных;
5. объём сетевого трафика;
6. количество регионов;
7. требования availability;
8. выбранный cloud provider;
9. объём observability;
10. характер массовых соревнований.

Поэтому расчёт должен регулярно уточняться после появления production-метрик.

---

# 12. Вывод

Архитектура позволяет начинать с относительно небольшой инфраструктуры и
масштабировать её по мере роста продукта.

Ориентировочная годовая стоимость инфраструктуры:

```text
Year 1     ≈ $85k
Year 2     ≈ $290k
Year 5     ≈ $1.8m
```

Наиболее значимыми статьями расходов на большом масштабе становятся:

- compute;
- databases;
- сетевой трафик;
- observability;
- multi-region infrastructure.

Поэтому архитектура не предполагает преждевременного внедрения дорогой
multi-region инфраструктуры.

Инфраструктурные возможности добавляются по мере подтверждения необходимости
реальной нагрузкой и бизнес-требованиями.
