# 15. Анализ рисков архитектуры и компромиссов

## 1. Цель анализа

На данном этапе анализируются риски, возникающие уже не только из бизнес-задачи,
но и из выбранной архитектуры системы.

Для каждого риска оцениваются:

- вероятность возникновения;
- влияние на систему;
- возможные последствия;
- способы снижения риска;
- остаточный риск после применения мер.

Для качественной оценки используется шкала от 1 до 5:

- 1 — очень низкий уровень;
- 2 — низкий;
- 3 — средний;
- 4 — высокий;
- 5 — очень высокий.

Итоговый Risk Score рассчитывается как:

`Probability × Impact`

# 3. Детальный анализ рисков

## AR-01. Рост сложности распределённой архитектуры

### Причина

Сервисная архитектура создаёт:

- сетевые взаимодействия;
- распределённые ошибки;
- необходимость service discovery;
- сложности локального тестирования;
- необходимость централизованной наблюдаемости.

### Последствия

- увеличение времени диагностики проблем;
- повышение стоимости эксплуатации;
- рост требований к квалификации команды.

### Mitigation

- не выделять сервис без явной причины;
- придерживаться крупных доменных границ;
- централизовать observability;
- стандартизировать создание и эксплуатацию сервисов;
- автоматизировать CI/CD.

### Остаточный риск

Средний.

Полностью устранить сложность распределённой системы невозможно.

### Связанные ADR

- ADR-001;
- ADR-013.

## AR-02. Eventual consistency

### Причина

Часть бизнес-процессов выполняется асинхронно через события.

Например:

```text
TrainingCompleted
       |
       +--> Analytics
       +--> Gamification --> AchievementEarned --> Event Bus --> Notifications
       +--> Recommendations
```

Результаты этих операций появляются не одновременно.

### Возможный сценарий

Пользователь завершил тренировку и сразу открыл статистику.

Тренировка уже сохранена, но новая статистика ещё не рассчитана.

### Mitigation

- явно определить сценарии, допускающие eventual consistency;
- показывать состояние обработки;
- устанавливать допустимые задержки;
- мониторить задержки consumers.

### Остаточный риск

Низкий / средний.

Для вторичных функций небольшая задержка допустима.

### Связанные ADR

- ADR-002;
- ADR-008.

---

## AR-03. Повторная доставка событий

### Причина

Message broker может повторно доставить сообщение после:

- сетевого сбоя;
- timeout;
- перезапуска consumer;
- отсутствия подтверждения обработки.

Outbox Publisher также может повторить публикацию при сбое между подтверждением
broker и отметкой записи в outbox. Transactional Outbox исключает разрыв между
сохранением тренировки и записью события, но не обеспечивает exactly-once доставку.

### Последствия

Без дополнительной защиты одно событие может:

- дважды выдать достижение;
- дважды изменить рейтинг;
- отправить два уведомления.

### Mitigation

Consumers должны быть идемпотентными.

Training сохраняет тренировку и Outbox Event атомарно (ADR-014). Publisher повторяет
публикацию до подтверждения; необходимо мониторить backlog и очищать опубликованные
записи. Эти меры не устраняют необходимость идемпотентности consumers.

Каждое событие содержит уникальный:

`EventId`

Перед выполнением операции consumer проверяет,
не было ли событие обработано ранее.

### Остаточный риск

Низкий.

### Связанные ADR

- ADR-002;
- ADR-008;
- ADR-014.

---

## AR-04. API Gateway как критическая точка отказа

### Причина

Внешний трафик проходит через API Gateway.

При его недоступности большая часть backend-функций становится недоступной.

### Mitigation

API Gateway должен:

- иметь несколько экземпляров;
- масштабироваться горизонтально;
- находиться за Load Balancer;
- не хранить пользовательское состояние;
- иметь health checks.

### Остаточный риск

Низкий.

### Связанные ADR

- ADR-004.

---

## AR-05. Сложность multi-region

### Причина

Глобальная платформа потенциально требует нескольких регионов.

Multi-region архитектура создаёт сложности:

- синхронизации данных;
- маршрутизации;
- failover;
- consistency;
- эксплуатации.

### Mitigation

Не использовать сложную active-active архитектуру до появления реальной
необходимости.

Развитие:

```text
Stage 1
Single Region

        ↓

Stage 2
Primary + Disaster Recovery

        ↓

Stage 3
Multi-Region
```

Окончательное решение должно основываться на:

- количестве пользователей;
- latency;
- требованиях availability;
- требованиях хранения данных.

### Остаточный риск

Средний.

### Связанные ADR

- ADR-011.

---

## AR-06. Раскрытие геолокационных данных

### Причина

Система хранит:

- маршруты;
- места тренировок;
- текущее местоположение;
- регулярные места пользователя.

Это потенциально чувствительная информация.

### Последствия

Возможность определить:

- место проживания;
- привычный маршрут;
- время отсутствия пользователя дома.

### Mitigation

- Privacy by Design;
- точное местоположение скрыто по умолчанию;
- пользователь управляет видимостью;
- минимальная необходимая точность;
- контроль доступа;
- аудит;
- шифрование.

### Остаточный риск

Средний.

### Связанные ADR

- ADR-009;
- ADR-010.

---

## AR-07. Зависимость от сторонних сервисов

### Причина

Система интегрируется с:

- wearable-устройствами;
- fitness API;
- системами компании.

Внешние API могут быть:

- недоступны;
- медленны;
- изменены;
- ограничены rate limits.

### Mitigation

Integration Layer должен использовать:

- timeout;
- retry;
- circuit breaker;
- rate limiting;
- очереди для фоновой синхронизации.

Отказ внешнего API не должен приводить к недоступности основного приложения.

### Остаточный риск

Средний.

### Связанные ADR

- ADR-007.

---

## AR-08. Стоимость observability

### Причина

Logs, metrics и distributed tracing могут создавать значительный объём данных.

Особенно опасно логирование каждого:

- GPS event;
- telemetry event;
- API request.

### Mitigation

- sampling traces;
- уровни логирования;
- ограниченный retention;
- агрегация метрик;
- запрет на запись чувствительных данных;
- разные сроки хранения различных типов telemetry.

### Остаточный риск

Средний.

### Связанные ADR

- ADR-013.

---

## AR-09. Избыточное количество сервисов

### Причина

Микросервисный подход может привести к попытке сделать отдельный сервис
для каждой небольшой функции.

### Последствия

- рост количества deployments;
- большое количество сетевых вызовов;
- рост затрат;
- сложная поддержка.

### Mitigation

Использовать правило:

> Новый сервис создаётся только при наличии необходимости независимого
> масштабирования, развёртывания, владения командой или изоляции отказа.

Малые функции могут находиться внутри более крупного доменного компонента.

### Остаточный риск

Низкий / средний.

### Связанные ADR

- ADR-001.

---

## AR-10. Рост инфраструктурных расходов

### Причина

Стоимость системы увеличивается вместе с:

- количеством пользователей;
- количеством тренировок;
- объёмом telemetry;
- сетевым трафиком;
- количеством регионов;
- сроком хранения данных.

### Mitigation

- autoscaling;
- lifecycle policies;
- архивирование старых данных;
- CDN;
- кеширование;
- sampling observability;
- регулярный FinOps-анализ;
- оптимизация наиболее дорогих компонентов.

### Остаточный риск

Средний.

# 4. Основные архитектурные компромиссы

## 4.1. Сервисная архитектура vs простота

### Выбрано

Сервисная архитектура.

### Получаем

- независимое масштабирование;
- изоляцию бизнес-доменов;
- независимую работу команд.

### Теряем

- простоту монолита;
- дешёвую локальную эксплуатацию;
- простые транзакции.

### Компромисс

Не создавать мелкие сервисы без необходимости.

---

# 4.2. Асинхронность vs строгая согласованность

### Выбрано

Event-driven обработка вторичных процессов.

### Получаем

- масштабируемость;
- отказоустойчивость;
- слабую связанность.

### Теряем

мгновенную согласованность данных.

### Компромисс

Критичные пользовательские данные сохраняются синхронно.

Вторичные данные могут обновляться с небольшой задержкой.

---

# 4.3. Доступность vs consistency

Во время массовых соревнований важнее продолжать принимать результаты
тренировок, чем мгновенно показывать абсолютно актуальный мировой рейтинг.

Поэтому:

```text
Training result:
stronger consistency

Leaderboard:
eventual consistency
```

---

# 4.4. Privacy vs social discovery

Чем больше информации о местоположении доступно системе и другим пользователям,
тем лучше работает поиск партнёров.

Но одновременно увеличивается privacy-риск.

Поэтому:

- социальный поиск является opt-in;
- публичная точная геолокация не требуется;
- используется минимально необходимая точность.

---

# 4.5. Надёжность vs стоимость

Multi-region active-active архитектура обеспечила бы очень высокую доступность,
но значительно увеличила бы стоимость и сложность.

Поэтому такая схема не используется на первом этапе развития системы.

Архитектура лишь сохраняет возможность перейти к ней в будущем.

---

# 4.6. Независимость сервисов vs дублирование данных

Для независимости бизнес-доменов допускается хранение локальных копий некоторых
данных.

Это повышает:

- автономность;
- производительность.

Но создаёт:

- дублирование;
- eventual consistency.

Компромисс считается приемлемым для read-моделей и аналитических данных.

---

# 5. Итог

Наиболее существенными архитектурными рисками являются:

1. рост сложности распределённой системы;
2. multi-region архитектура;
3. защита геолокационных данных;
4. рост стоимости инфраструктуры.

Для снижения этих рисков архитектура развивается постепенно.

На ранних этапах не внедряются сложные инфраструктурные механизмы,
пока их необходимость не подтверждается фактической нагрузкой и
бизнес-требованиями.
