# 10. Архитектурные опции

На концептуальном этапе рассматриваются три основных варианта.

## Вариант A. Монолит

```text
Mobile
|
v
Backend
|
+-- Users
+-- Training
+-- Social
+-- Gamification
+-- Promotions
+-- Integrations
|
Database
```

### Преимущества

- Минимальная сложность.
- Простая разработка.
- Простое локальное тестирование.
- Низкая стоимость первоначальной эксплуатации.

### Недостатки

- Сложнее независимо масштабировать наиболее нагруженные части.
- Рост связности по мере развития системы.
- Большое количество команд может мешать друг другу.
- Сложнее независимо развивать разные бизнес-возможности.

### Решение

Не выбирается как целевая архитектура глобальной платформы.

При этом модульный монолит может использоваться для отдельных компонентов или раннего MVP.

## Вариант B. Микросервисная архитектура

```text
API
|
 -----------------------------------
|       |       |        |         |
User  Training Social  Analytics  Promo
|       |       |        |         |
 -----------------------------------
                |
             Events
```

### Преимущества

- Независимое масштабирование.
- Независимый жизненный цикл компонентов.
- Удобство работы нескольких команд.
- Возможность использовать разные технологии при необходимости.
- Хорошая изоляция бизнес-возможностей.

### Недостатки

- Высокая эксплуатационная сложность.
- Распределённые транзакции.
- Сложная наблюдаемость.
- Проблемы согласованности данных.
- Более сложное тестирование.

## Вариант C. Event-driven микросервисная архитектура

Основные бизнес-компоненты взаимодействуют синхронно там, где пользователю необходим немедленный ответ, а вторичные реакции выполняются через события.

Пример:

```text
Training Service
|
| TrainingCompleted
v
Event Bus
|
  -----------------------------
|           |              |
v           v              v
Analytics Gamification Notifications
```

### Пример

После окончания тренировки Training публикует:

`TrainingCompleted`

После чего независимо могут выполняться:

- Пересчёт статистики.
- Проверка достижений.
- Изменение рейтинга.
- Уведомление друзей.
- Обновление рекомендаций.

## Выбранный подход

В качестве целевого варианта выбирается:

доменная сервисная архитектура с event-driven взаимодействием для асинхронных сценариев.

Это не означает необходимость превращения каждого небольшого компонента в отдельный микросервис.

Границы сервисов должны определяться бизнес-возможностями и необходимостью независимого масштабирования.

### Причины выбора

#### 1. Масштаб

Отдельные части системы имеют принципиально разные профили нагрузки.

Например:

- Запись тренировок.
- Социальная активность.
- Расчёт рейтингов.
- Рассылка уведомлений.

#### 2. Массовые соревнования

Во время соревнования Analytics и Gamification могут испытывать гораздо большую нагрузку, чем Profile или Equipment.

Их необходимо масштабировать независимо.

#### 3. Большое количество команд

Компания имеет большой штат разработчиков.

Разделение по бизнес-возможностям позволяет различным командам независимо развивать части платформы.

#### 4. Интеграции

Система должна работать с большим количеством внешних источников данных.

Изолированный integration layer уменьшает связанность основной системы с конкретными производителями.

#### 5. Event-driven обработка

Большинство действий после тренировки не требуют синхронного выполнения.

Например:

```text
Training completed
|
+--> statistics
+--> achievements
+--> rankings
+--> notifications
+--> recommendations
```

Поэтому их можно выполнять асинхронно.
