# ADR-013. Централизованная наблюдаемость

**Статус:** Accepted

## Context

Сервисная и event-driven архитектура значительно сложнее в диагностике, чем
монолитное приложение.

Один пользовательский сценарий может проходить через несколько компонентов и
асинхронных обработчиков.

Без централизованной наблюдаемости сложно определить:

- где произошла ошибка;
- какой сервис вызвал задержку;
- было ли событие обработано;
- насколько загружены компоненты.

## Decision

Использовать централизованную observability-платформу.

Основные сигналы:

- logs;
- metrics;
- distributed traces;
- alerts.

Для распределённого сценария должен передаваться correlation identifier,
позволяющий связать операции между компонентами.

Пример:

```text
RequestId: abc-123

Mobile
   |
   v
API Gateway
   |
   v
Training
   |
   v
TrainingCompleted
   |
   +--> Analytics
   +--> Gamification
```

Один correlation ID позволяет проследить весь сценарий.

## Alternatives

### Локальные логи каждого сервиса

Отклонено как основной подход из-за сложности поиска проблем в распределённой
системе.

### Наблюдаемость только критических сервисов

Отклонено, поскольку сбой может происходить на границе компонентов.

## Consequences

### Positive

- упрощение диагностики;
- возможность контролировать SLA/SLO;
- поиск проблем в распределённых сценариях;
- мониторинг очередей и фоновых процессов.

### Negative

- дополнительная инфраструктура;
- стоимость хранения telemetry;
- необходимо контролировать попадание персональных данных в логи.
