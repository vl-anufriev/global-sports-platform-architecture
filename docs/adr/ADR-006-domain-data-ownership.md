# ADR-006. Владение данными доменными компонентами

**Статус:** Accepted

## Context

При использовании сервисной архитектуры общая база данных создаёт сильную
связанность между компонентами.

Изменение структуры таблицы одним компонентом может нарушить работу других
компонентов.

## Decision

Каждая доменная область является владельцем своих данных.

Например:

- Profile — данные профиля;
- Training — тренировки;
- Social — социальные связи и группы;
- Gamification — достижения и соревнования;
- Equipment — инвентарь;
- Promotions — акции.

Один компонент не должен напрямую изменять данные другого компонента.

Взаимодействие выполняется через:

- API;
- доменные события.

Это логическое владение данными.

Физически несколько компонентов на ранних этапах могут использовать одну СУБД
при условии разделения схем и отсутствия прямых междоменных запросов.

## Alternatives

### Единая общая модель данных

Отклонена из-за сильной связанности.

### Полностью отдельная СУБД для каждого компонента с первого дня

Не является обязательным требованием.

Это может привести к избыточной инфраструктурной сложности на раннем этапе.

## Consequences

### Positive

- независимое развитие доменов;
- явная ответственность за данные;
- уменьшение связанности.

### Negative

- возможна eventual consistency;
- часть данных приходится дублировать;
- междоменные запросы становятся сложнее.
