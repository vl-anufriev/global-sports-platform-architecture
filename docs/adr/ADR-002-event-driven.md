# ADR-002. Event-driven взаимодействие

**Статус:** Accepted

## Context

Одно бизнес-событие может инициировать несколько независимых процессов.

Например, после завершения тренировки необходимо:

- пересчитать статистику;
- проверить достижения;
- обновить рейтинг;
- сформировать рекомендации;
- отправить уведомления.

Выполнение всех этих действий синхронно увеличивает задержку пользовательского
запроса и создаёт сильную связанность между компонентами.

## Decision

Использовать event-driven взаимодействие для операций, которые не требуют
немедленного результата пользователю.

После успешного сохранения тренировки Training публикует событие:

`TrainingCompleted`

Событие независимо могут обрабатывать:

- Analytics;
- Gamification;
- Notifications;
- Recommendations.

```text
Training
    |
    | TrainingCompleted
    v
 Event Broker
    |
    +--> Analytics
    +--> Gamification
    +--> Notifications
    +--> Recommendations
```

## Alternatives

### Только синхронные API-вызовы

Training последовательно вызывает остальные компоненты.

Отклонено, потому что:

- повышает задержку;
- создаёт сильную связанность;
- отказ одного компонента может повлиять на основной сценарий.

### Общая база данных

Компоненты обнаруживают изменения через общие таблицы.

Отклонено из-за:

- сильной связанности данных;
- отсутствия явного контракта;
- сложности независимого развития компонентов.

## Consequences

### Positive

- слабая связанность;
- независимое масштабирование;
- отказ потребителя не блокирует Training;
- легко подключать новых потребителей событий.

### Negative

- eventual consistency;
- усложнение отладки;
- требуется обработка повторных сообщений;
- требуется мониторинг очередей.
